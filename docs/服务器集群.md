## 三个不同的公网 IP —— 这是并行拉数据的前提

新浪等数据源按【出口 IP】限流。已实测三台出口 IP 互不相同, 所以三机并行拉取
是真的 3 倍, 不是假并行。这决定了哪些活值得分布式:

| 任务 | 单机耗时 | 并行价值 | 原因 |
|---|---|---|---|
| K线回灌 | ~40min | 低 | 单机够快, 不值得折腾环境 |
| 资金流回灌到2015 | 6~10h | **高** | 受 IP 限流, 3 IP = 3 倍 |
| eval 缓存构建 | 4.5h | **高** | CPU 密集, 384 核可用 |
| 单次回测 | 分钟级 | 低 | 本来就快 |

## 免密 SSH (2026-08-04 配置)

三机全互通(跨机 6 个方向已验证)。做法:
- 每台用**自己原有的**密钥(eez041 是 ed25519, 040/042 是 rsa), 不共用私钥
- 三个公钥**去重追加**进每台的 `~/.ssh/authorized_keys` (原文件已备份为
  `authorized_keys.bak_<时间戳>`), 权限 700/600
- 互加 host key 到 `known_hosts`

自己连自己会失败(短主机名不在 known_hosts), 但从不需要, 忽略即可。
`rsync` 三台都有, 已验证 eez041 -> 040/042 通路正常。

## 分布式拉取: scripts/pull_fundflow_shard.py

按 code 的 MD5 哈希取模分片, 而不是按顺序切段 —— 顺序切会让老股票集中在一片,
各片历史长度差很多导致耗时不均; 哈希取模天然打散, 且同一只股票永远落在同一片,
断点续跑不会换机器重复拉。已验证三片不重不漏、大小均衡、结果稳定可复现。

```bash
# 三台各跑一片 (--codes-file 必须三台用同一份, 否则分片不一致会漏拉)
ssh eez040 'cd ~/quant-strategy && python3 scripts/pull_fundflow_shard.py --shard 0 --of 3 --since 2015-01-01 --codes-file /tmp/codes.txt'
ssh eez041 '... --shard 1 --of 3 ...'
ssh eez042 '... --shard 2 --of 3 ...'
# 收集分片到主节点后合并 (缺片会拒绝合并, 避免静默得到残缺池子)
ssh eez041 'cd ~/quant-strategy && .venv/bin/python scripts/pull_fundflow_shard.py --merge --of 3'
```

## K线数据源: 三个源的前复权口径不一致 (2026-08-04 发现并修复)

`update_kline_akshare.fetch_one` 按 新浪 -> 东财 -> 腾讯 三级 fallback。
**三个源的前复权口径不同**: 同一只股票(实测 000001 平安银行), 新浪与腾讯的
日收益率最大差 **3.1%**, 相关性 0.998 而非 1.0 —— 复权后的收益率本身就不一样,
不只是价格水平的差异。

原实现是"新浪一失败立刻换源", 限流稍微抖一下就降级。后果比"少数股票口径不同"
严重得多 —— **训练数据不可复现**:

| 同一批 400 只, 前后两次全量拉取 | 只数 |
|---|---|
| 回灌前走备用源 | 23 |
| 回灌后走备用源 | 24 |
| **本次新变成备用源** | **16** |
| **本次修回正常源** | **15** |

也就是每次拉取约 6% 的股票随机落到不同口径的源, **且每次是哪些股票都不一样**。
同样的代码同样的参数, 两次拉取得到不同的价格序列, 于是特征筛选、IC、回测结论
都会漂移。(这可能部分解释了为什么两个窗口的特征筛选只重叠 35/80。)

**修法**: 新浪带退避重试 3 次再降级 + 把实际来源写进
`data/raw/kline_source_manifest.json`。每次拉取都打印来源分布, 并提示
"本次有 N 只股票的来源发生变化 -> 它们的历史收益率被改写"。
manifest 是**合并**写入而非覆盖, 否则 `--codes` 这类部分拉取会抹掉其余记录。

## 幸存者偏差: 已退市股只有腾讯源有数据

2015 前上市的 2892 只里有 120 只没有 K线, 分类后:

| 类别 | 只数 | 处置 |
|---|---|---|
| 2015-07 **前**已退市 | 94 | 不管 —— 当时就不可投 |
| **2015-07 后才退市** | 26 | **必须补**, 否则幸存者偏差 |
| 从未退市却缺数据 | 0 | 无异常 |

26 只剔掉 B股(本就在排除列表)后是 16 只(武钢股份/招商地产/小天鹅Ａ/欣泰退…),
它们在 2015-2019 是真实可投的, 后来才退市。**只有腾讯源能取到**。

**决定: 补, 并在 manifest 里标记来源。** 理由:
- 幸存者偏差是**系统性、单向**的 —— 只会让回测好看, 而消除虚高正是这轮工作的核心
- 口径差异是**随机、双向**的, 且只影响 16/300 ≈ 5%, 不偏向任何方向
- 这 16 只本来就要退市, 模型在它们身上大概率是亏的, 补进去只会让回测更保守

标记来源是为了留一条后路: 可做敏感性分析(带/不带这 16 只各跑一遍), 看结论
是否被它们改变。

## 注意

- **实盘只跑在 eez041**: 定时任务 `quant-daily.timer` 每天 17:30/19:30/21:30,
  会写 `data/raw/kline` 与 `data/live`。跑全量重拉前必须确认它没在跑,
  否则两边同时写同一批文件。
- K线写入是原子的(先写 `.tmp.parquet` 再 rename), 所以中断不会让实盘读到
  半个文件; 但会留下"部分股票已回灌、部分还是旧起点"的混合状态, 可重跑补齐。
## 代码同步 (2026-08-10 起主节点走 git)

**主节点 eez041 已是真 git 仓库**, `origin` 指向 `git@github.com:aweakdog/QuantMyBrother.git`。
在此之前它只是同步副本, 靠 `check_server_sync.py --push` 保障一致性。

改这个的直接原因: 那套机制是**单向**的(本地 → 服务器), 无法判断哪边更新。
2026-08-10 上午本地 `live_config.py` 还是 F1B、服务器已上线 F7, 这期间任何人跑
一次 `--push` 都会把线上特征集**回退成 F1B** —— F7 矩阵里没有 `mf_*` 列, 护栏会
判"缺列"直接硬拦, 当晚无信号。而 `live_config.py` 正在 `MAIN_FILES` 清单里。

第二个原因是清单必然会漏。`pipeline/pull_tushare.py` 是日更拉 tushare 数据的
关键脚本, 却既不在清单里也不在 git 里, 双重无保护; 一起补进来的还有 10 个
PIT 股票池文件(窗口A 的全部回测都依赖 `universe_pit_2019.parquet`)。

现在的工作流:

| 改动发生在 | 怎么走 |
|---|---|
| 本地 | 本地 commit + push, 服务器 `git pull` |
| 服务器 | 服务器 commit + push, 本地 `git pull` |
| 任何时候想确认 | `python scripts/check_server_sync.py` |

`check_server_sync.py` 仍然是核对入口, 但对主节点改成了 git 校验(比 HEAD +
看工作区是否干净, 覆盖全部文件), 且 `--push` **拒绝**作用于主节点。
计算节点 eez040/042 没有 git, 仍是哈希比对 + scp, `--push` 只对它们生效。

- **服务器 push 到 GitHub 需要 Deploy key**: 把 eez041 的 `~/.ssh/id_ed25519.pub`
  加到仓库 Settings → Deploy keys 并勾选 **Allow write access**。没加之前服务器
  只能收不能发(仓库是用 `git bundle` 从本地引导建立的)。
